# AIDM API 2.8.0: Windows native packages, the host option, a task list that survives a kill

Issue: https://github.com/AIDroneMap/aidm-api/issues/92

Written from the engine repository's design note `docs/design/windows-engine-0.3.0.md` (aidm PR #112), its ADR 0005 to ADR 0007, this repository's ADR 0001 to ADR 0004, and the words in `GLOSSARY.md` of both repositories. The note records the decisions and the facts they rest on; this spec says what has to be true on `master` for `v2.8.0` to be tagged, and how each part is proven. The tickets are cut from the "Implementation decisions" and "Testing decisions" sections, one pull request each.

## Problem statement

A pilot on Windows who installs the interface today is told that Windows is not supported yet. The engine manager installs a native package only from a signed release manifest, and no release of this API has ever listed a native variant. The README says it: on Windows only test mode works, because there is no Windows engine. Engine 0.3.0 changes the second half. Its tag run publishes an engine archive for `windows-x64` and one for `windows-x64-cuda`. Nothing turns those into a package the interface can install.

When the interface starts the API on a pilot's laptop, the API binds its port on every network interface of the machine, and its UDP progress receiver too. The token is the only wall between the task API and the office network. The API has no option to bind to loopback only. `--socket` does not help: it is refused on Windows.

The interface stops a native package with `taskkill /PID <pid> /T /F`. The API writes its task list to disk once an hour and at a clean stop, on SIGTERM or SIGINT, which `taskkill` never sends. At the next start the API deletes every task folder that has no entry in the list. A pilot who closes the interface an hour after a run therefore loses the run's results, not only its entry.

## Solution

2.8.0 is the API half of AIDroneMap 0.3 on Windows, released after engine 0.3.0 and before interface 0.3.0 (aidm ADR 0007).

A `--host` option and a `host` config key bind the HTTP listener and the UDP progress receiver to one address. The interface writes `host: "127.0.0.1"` for a native package, and the task API is then reachable from the machine only.

The API writes its task list whenever it changes, through a temporary file renamed into place, so a kill at any moment leaves a complete list on disk and the next start keeps every task and its results.

The tag run pins the two engine archives by SHA-256, downloads them from the engine release, places the files of its own Windows zip at the root and the engine under `engine/`, and publishes one native package per variant as its own release assets. The signed manifest lists both, the CUDA one with the driver floor `minimumDriverVersion`. The same run unpacks each package on a hosted Windows runner, starts it the way the interface does, reads the engine's version and option list through it, sends it one task the engine refuses, and stops it with `taskkill`.

The release ticket moves the version to 2.8.0, the base images to engine 0.3.0, and the engine archive pins to the 0.3.0 hashes. The API tags once the engine tag exists and every ticket is merged.

## User stories

### Reaching the API on one address

1. As a pilot on Windows, I want the task API that the interface starts to listen on loopback only, so that nothing on my office network can reach it.
2. As the interface's builder, I want a `host` key in the config file next to `port` and `token`, so that I write one file as I do today.
3. As an operator who starts the API by hand, I want a `--host <address>` flag with the same meaning as the key, so that the command line and the file agree.
4. As an operator of an existing installation, I want the default unchanged when I set no host, so that nothing I run today changes behaviour.
5. As an operator, I want the UDP progress receiver bound to the same address as the port, so that the progress port is not open where the HTTP port is closed.
6. As an operator, I want the API to refuse to start, with an error that names the address and the port, when the address is not one this machine has, so that a typo never leaves me with a server I cannot find.
7. As an operator who uses `--port auto`, I want the search for a free port to stay a search for a free port, so that a wrong address does not try every port up to the limit before it fails.
8. As a maintainer, I want the startup log to say the address and the port the API listens on, so that a diagnosis log has the fact.
9. As an operator, I want the help text to say that the engine sends progress to 127.0.0.1, so that I know why a host other than loopback or 0.0.0.0 shows no progress.
10. As a client, I want the same routes and the same token check on a bound address as on every interface, so that nothing else changes.
11. As a reader of the README, I want `--host` in the options table, so that the documentation matches the help.

### A task list that survives a kill

12. As a pilot, I want a task I created five minutes ago to still exist after the interface stopped the API with `taskkill`, so that closing the interface loses nothing.
13. As a pilot, I want the results of a completed run kept after a kill, so that the next start does not delete a folder it no longer knows.
14. As a pilot, I want a task that was running when the API was killed to come back queued and run again, so that I do not have to upload the images twice.
15. As an operator, I want the list on disk to be complete JSON at every moment, so that a kill during a write never leaves a corrupt file and an empty list.
16. As an operator, I want the list written when a task is added, removed, restarted or changes state, so that every event a client can see is on disk.
17. As an operator, I want progress updates kept out of the trigger, so that a running task does not write the file many times a second.
18. As an operator, I want a write failure logged and the request still answered, so that a full disk fails loudly but does not break the API.
19. As a maintainer, I want the file format unchanged, so that a 2.7.0 list restores into 2.8.0 and the other way round.
20. As a maintainer, I want the hourly write and the write at a clean stop kept, so that the old paths still exist for an installation that never changes a task.

## Implementation decisions

### Binding to a host

- Flag `--host <address>`, config key `host`, no default. Absent, the API listens on every interface, as today. Configuration stays compatible: no flag or key is renamed or removed.
- The HTTP listener binds the port on the host, for a fixed port and for `auto`. The search for a free port moves on only when the port is in use, as today. Any other bind error fails the start with a message that names the address and the port.
- The progress receiver binds its port on the same host. Its bind error stays a warning, as today, and its log line already names the bound address. The engine sends progress to 127.0.0.1, so a host that is neither a loopback address nor the unspecified address receives none; the help text says so.
- The startup log names the address and the port when a host is set. The line stays as it is when none is set.
- The socket option does not change, and neither does its refusal on Windows. The token check and every route are the same on a bound address.
- The help text and the README's options table gain the flag. The API specification and the Swagger file do not change, because no response changes.

### The task list on disk

- A change is one of: a task added, a task removed, a task restarted, a task's status code changed. Progress, output lines and processing time are not changes. A running task that comes back after a kill is queued again and starts over, as the restore already does, so its progress is not needed on disk.
- One function writes the list. It serializes every task as today, writes the whole list to a temporary file in the data folder, and renames it over the list file. The rename replaces the old file, so a kill at any moment leaves the previous complete file or the new one, never a partial one. On Windows the dry run's executable proves the replace.
- At most one write runs at a time. A change that arrives during a write starts one more write when it ends. A burst of changes costs two writes.
- A write error is logged, as today, and never fails the request or the task that caused it.
- The hourly write and the write at a clean stop stay. The file name and the serialized form do not change.
- The task tells its manager when its status code changes; the manager owns the write. How the task reaches the manager is the builder's choice, as long as a task restored from disk reports too.

### Engine archives pinned

- A sums file in the scripts folder, next to the Bun and 7-Zip sums, names the engine version and, for each of the two engine archives, its file name and SHA-256. The CUDA line also carries the driver floor. For engine 0.3.0 that is `576.57` (aidm ADR 0006).
- A unit test fails when the engine version in the sums file is not the one the Dockerfile names. The version-strings test is the pattern.
- A download script fetches one engine archive from the engine release named by that version, from the engine repository's release assets, and checks it against the sums file. A mismatch fails. The 7-Zip download script is the pattern.
- Before engine 0.3.0 is released the sums file names 0.2.0 and lists no archives. The workflow reads that as "no native packages" and says so in the log.

### Native packages assembled

- A script in the scripts folder takes a variant, the API's Windows zip and the matching engine archive, and writes one native package: `aidm-native-<api version>-windows-x64.tar.gz` or `aidm-native-<api version>-windows-x64-cuda.tar.gz`, with one top folder of the same name without the extension.
- The top folder holds the files of the API's Windows zip at its root, so the executable `aidm-api.exe`, `helpers`, `apps/7z`, `config-default.json`, `public`, `docs/swagger.json`, `tests`, `tmp`, `data`, `LICENSE`, `SOURCE` and the third-party notices are where the interface expects the API. The engine archive's `engine/` folder is placed under it as `engine/`.
- The script refuses an engine archive that does not hold exactly one top folder with `engine/` under it, or whose `engine/VERSION` does not say the pinned engine version, or that lacks `engine/run.bat` or `engine/win32env.bat`.
- File order, owners and times are fixed, with the same tar settings the release archives use, so the same inputs give the same bytes.
- The script writes, next to the package, a description file with the package's file name, size in bytes and SHA-256. The manifest reads the description, never the package.
- A package that passes the size limit of a release asset fails the step with its size in the message. The maintainer then decides about the project's object storage, which needs a secret and is outside this spec.

### The manifest's native entries

- The manifest script's `build` command accepts the description files. With them it adds two variants after the three container ones, in this order: `windows-x64` with `kind: "native"`, `url`, `size`, `sha256`, `gpu: false`; then `windows-x64-cuda` with the same keys, `gpu: true` and `minimumDriverVersion` from the sums file, a string of the form major dot minor, such as `576.57`.
- `url` is the release asset address of this repository for the run's version: `https://github.com/AIDroneMap/aidm-api/releases/download/v<version>/<file>`. A dry run writes the same form; the asset does not exist then, and the interface's parser checks only that the address is https.
- Without description files the manifest has three variants, as 2.7.0's has.
- The file is still written once, with fixed key order and formatting, and the signature covers exactly those bytes. `sequence` for 2.8.0 is 2008000. `minimumUiVersion` stays 0.1.0, as decided: an interface that does not know `windows-x64-cuda` skips it and reads the rest, and the Windows check of a 0.2.x interface still refuses Windows.

### The workflow

- The check job reads the sums file and says whether the pinned engine has Windows archives. Every Windows job reads that output.
- A new job on Linux, after the check and the executables jobs, runs when the archives exist. It downloads the executables artifact, fetches the two engine archives with the download script, assembles the two packages, writes their sums and descriptions, and uploads the packages as one artifact and the descriptions as another, small one.
- The manifest job downloads the descriptions when they exist and passes them to the script. The dry run's manifest check expects five variants when they exist and three when they do not. Its pin of the interface repository moves to a commit that knows `windows-x64-cuda` and `minimumDriverVersion`, because the pinned verifier fails on any variant id it does not know. That pull request therefore lands after the interface's schema ticket.
- A new job on the hosted Windows runner the executables test already uses, one matrix entry per variant, runs when the packages exist. It downloads the package, checks its sum, unpacks it with the system `tar`, writes a config file with `port`, `token`, `host` set to loopback, `parallelQueueProcessing` 1 and `odx_path` pointing at `engine/` inside the package, and starts the executable with `--config`. It waits for `/info` on loopback with the token, checks that `/info` names the pinned engine version, checks that `/options` returns a non-empty list, creates one task with one small image, waits for the task to end, checks that it ended failed with lines written by the engine in its output and without the API's "Could not start process" message, stops the process with `taskkill /PID <pid> /T /F`, and checks that no process of the tree remains. No engine run on real images: the engine's own Windows job does that. The line it expects from the engine is read from the first run's log, not from memory.
- The draft release job uploads the native packages and their sums with the other assets, and the notes gain a section with the engine version and a table of the packages.
- Every job downstream of a job a dry run may skip starts its condition with `!cancelled()` and names the results it needs, as the rules of this repository require. After each dry run the builder checks that no job the change needs was skipped.
- Dry runs build, test and describe the packages and publish nothing, as today. Timeouts for the new jobs come from the first run that has real archives; none is claimed here.
- A pull request that touches the workflow changes nothing else. The native-packages job, the manifest wiring and the Windows start check are three workflow pull requests.

### The rule files

- The rule that the inherited batch files are not maintained and must not be edited changes in a pull request of its own, after the start check has run green on a package: the Windows helper is then a maintained file with a test. The README's Windows sentence changes in the release ticket, when a release has the packages.

### The release ticket

- Every file the version test checks says 2.8.0. The CPU Dockerfile and the Apptainer definition move the base to engine 0.3.0, the GPU Dockerfile to its GPU tag. The sums file names 0.3.0 and the two archives with the hashes read from the engine release's sum files.
- `## Unreleased` becomes `## 2.8.0`, with a paragraph at the top that tells the release as a whole: engine 0.3.0, the native packages for Windows, the host option, the task list on every change.
- Blocked by the engine tag `v0.3.0` and by every other 2.8.0 ticket. Its dry run is the first run with real engine archives and the rehearsal of the tag run.
- Tag order: the API tags when `v0.3.0` exists and every ticket is merged; the interface pins the published manifest after that.

### The taggable minimum

1. The host ticket merged.
2. The task list ticket merged.
3. The sums file, the download script and the assembly script merged, with their unit tests.
4. The manifest script's native entries merged, with their unit tests.
5. The three workflow pull requests merged, the manifest wiring after the interface's schema ticket.
6. Engine `v0.3.0` tagged, with its two engine archives and their sums on the release.
7. The release ticket merged after a dry run that assembled both packages, started both on the Windows runner, and produced a five-variant manifest the interface's verifier accepted; then the tag is pushed and the tag run is green, with the packages, `manifest.json` and `manifest.json.sig` on the draft release.

## Testing decisions

A good test checks what a client, the interface or an operator sees: a response on an address, a file on disk after a kill, a folder in an archive, an entry in the manifest, a process that is gone. It does not check how the code got there. The compatibility harness in test mode is the highest existing seam and takes what a scenario can express. Unit tests take what the harness cannot reach: a refusal at startup, a kill, a script on fixture inputs. The dry run is the only seam for the workflow, and the maintainer starts it.

### Seams

- Compatibility harness, test mode. One new scenario, `host`: the API started with `--host 127.0.0.1`, the steps of the default scenario, a golden file that matches the default one for the same routes. The dry run runs it on the three executables, Windows included.
- Unit tests in the child-process pattern of the socket test. For the host: `/info` answers on loopback when the host is loopback; a start with an address this machine does not have fails with an error that names it, and with `--port auto` it fails without walking the port range; the progress receiver bound to a host delivers a datagram sent to that host. For the task list: start the API in test mode with a test task that takes a few seconds, create a task, kill the process with no signal it can catch, start it again, and the task is listed and queued; a completed task is still listed after the same kill. For the write: a burst of changes leaves one complete file whose content is the last state and no temporary file; a failing write is logged and the caller is answered.
- Unit tests for the scripts, in the pattern of the 7-Zip download test and the manifest test. The download script fails on a sum mismatch and passes on a match, against a local file. The assembly script, on fixture archives of a few files, produces the layout, refuses a wrong engine archive, and gives the same bytes twice. The manifest script writes the two native entries in order, the driver floor on the CUDA entry only, the address form, and refuses a description without a sum; the output stays byte-exact. The sums file's engine version equals the Dockerfile's.
- The maintainer's dry run, started on the pull request head when the pull request is open and linked in the description, so the reviewer judges its results as `REVIEW.md` requires. Until engine 0.3.0 is released, a dry run proves only that the Windows jobs skip with their reason and that the rest is unchanged. The release ticket's dry run is the first real one. A failure there is fixed in a workflow pull request of its own before the tag.

### Per ticket

| Ticket | Tests | Depth |
| --- | --- | --- |
| Host option and key | The host unit tests; the `host` scenario; the dry run runs the scenario on the three executables. | `full`: a configuration key and a flag, which the rules keep out of `unit`. |
| Task list on every change | The kill-and-restart unit tests; the write unit tests; the harness unchanged. | `full`: the rename on Windows is proven only by the Windows executable in the dry run. |
| Sums file, download script, assembly script | Their unit tests; the version pin test. | `full`: the scripts folder. |
| Manifest script native entries | The manifest unit tests extended. | `full`: the manifest. |
| Workflow: native-packages job and release assets | The dry run; before engine 0.3.0, the skip with its reason. Workflow files only. | `full` |
| Workflow: manifest wiring and the interface pin | The dry run's manifest check with five or three variants. After the interface's schema ticket. Workflow files only. | `full` |
| Workflow: Windows start check | The dry run on both packages; before engine 0.3.0, the skip. Workflow files only. | `full` |
| Rule files: the batch file line | Reading; the unit tests. After the start check has run green. | `unit` |
| Release 2.8.0 | The version test; the harness; the dry run on the final branch with real archives. | `full` |

Order: the host and task list tickets any time; the scripts ticket, then the manifest script ticket; the three workflow pull requests after both, one at a time, the manifest wiring after the interface's schema ticket; the rule files after a green start check; the release ticket last, after `v0.3.0`. At most three dry runs in parallel across the organisation's repositories. A second dry run on one pull request only when its head moves.

Prior art: the socket test starts the API in a child process on a temporary folder; the storage and HTTP client tests listen on loopback; the 7-Zip download test and the pushed-image check test run scripts from the scripts folder against cases; the manifest test checks byte-exact output and the sign-and-verify round trip; the harness holds the scenarios and the normalisation; the task schedules test loads the manager with its dependencies replaced.

## Out of scope

- A macOS native package (#24): needs a macOS engine build.
- The project's object storage for a package that passes the asset limit: the maintainer's decision, with a size from a run, and a secret. Nothing here reads or needs a new secret, environment or repository setting.
- Signing the Windows executable: the interface's release notes step and the signing service decision live there.
- A configurable progress port, or progress over anything but UDP on 127.0.0.1.
- A named pipe or any socket on Windows.
- Removing the inherited batch files. The helper is used as it is; only its rule line changes.
- An engine run on real images in this repository's workflow. The engine's Windows job does that, through the last released API.
- Lifting the interface's Windows refusal, the machine checks and the driver comparison: the interface's spec.
- The two open bugs #87 and #88: on their own.
- Benchmarks: nothing here changes an engine run.

## Further notes

- Values the interface session matches: variant ids `windows-x64` and `windows-x64-cuda`; the key `minimumDriverVersion`, a string, present on the CUDA entry only; config key `host`; a package of one top folder with `aidm-api.exe` at the root and the engine under `engine/`; assets `aidm-native-<version>-windows-x64.tar.gz` and `aidm-native-<version>-windows-x64-cuda.tar.gz` with `SHA256SUMS`; `sequence` 2008000; `minimumUiVersion` 0.1.0.
- A container whose port the container tool publishes is reached through the container's own address, not loopback. A `host` of 127.0.0.1 in a container's config would cut the interface off. Which configs carry `host` is the interface spec's decision; this API only offers the key.
- No run has yet shown the compiled executable starting `run.bat` on Windows. The one-task step of the start check is the first proof. If it fails for a reason in this repository, the fix is a ticket here, and the engine's Windows smoke test waits for it, because that test drives the engine through the last released API.
- The Windows helper calls the engine's `win32env.bat` and then `python`. The engine's new `win32env.bat` puts the package's own Python first on the path, so the helper runs the embedded interpreter without a change. If the start check shows the helper needs a change, the rule line about the batch files changes in that pull request.
- The maintainer: checks that the GPU environment's branch policy covers every builder branch prefix before the first dry run; starts each dry run on the pull request head when asked; reads the sizes of the two packages in the release ticket's dry run and decides about object storage if one passes the limit; publishes the draft release when the tag run is green, after `v0.3.0` exists.
- Nothing here needs a new dependency, a new bundled tool or a new external service.
