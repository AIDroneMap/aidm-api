# AIDM API 2.7.0: what the release ships and how it is proven

Issue: https://github.com/AIDroneMap/aidm-api/issues/71

Written from the design note `docs/design/api-2.7.0.md`, ADR 0001 to ADR 0004, and the words in `GLOSSARY.md`. The note records the decisions and the facts they rest on; this spec says what has to be true on `master` for `v2.7.0` to be tagged, and how each part is proven. The tickets are cut from the "Implementation decisions" and "Testing decisions" sections, one pull request each.

## Problem statement

An operator who installs aidm-ui today cannot install a current engine from it. The engine manager installs only from a signed release manifest, and no release of the task API has ever published one; the only engine it can install is 2.5.0, through a built-in entry.

An operator on a Mac who runs the local engine in Apple's container tool loses it whenever the Mac's routing or its local-network permission gets in the way, because the API can be reached only through a published port. The API cannot listen on a socket.

An operator whose photos already sit on the engine's machine, or on a folder aidm-ui can mount into the engine's container, has every flight copied into the task folder, because the API takes images only as uploads or as the address of a zip file.

An operator who runs a release archive on a machine without `unzip` and `7z` on the path gets failing zip uploads, because the archives ship no tool and the Windows archive has never been tested with one.

Every client of `/info` reads two fields that name a reference project's version. One of them will have no source once engine 0.2.0 stops writing the file it comes from.

After 2.7.0 the API pauses new development. Whatever is missing from this release stays missing for a long time.

## Solution

2.7.0 is the API half of AIDroneMap 0.2, released with engine 0.2.0 and the first aidm-ui tag.

Every tag run publishes `manifest.json` and `manifest.json.sig`, signed with the signing key from the release environment and verified against the committed public key before upload. aidm-ui installs 2.7.0 from that manifest and reads from it that the API can be reached through a socket.

The API listens on a Unix socket path next to its port when asked, so Apple's tool relays it to the Mac without any IP network.

A task can be created from a folder the API can read, under a root the operator or the engine manager configures. The API links the photos into the task's images folder instead of copying them, never writes into the source, and says in `/info` that it can.

Every release archive bundles 7-Zip, pinned and checksummed, with its licence in the notices, and the compiled executables are tested with that tool alone on every platform.

The two upstream fields leave `/info`, the startup log and the docs. The compatibility harness passes with its golden files changed only by that removal.

The release ticket moves the version to 2.7.0 everywhere, the base image to engine 0.2.0, and the changelog into lines a user can read. The API tags once the engine tag exists and every ticket is merged.

## User stories

### Installing from the manifest

1. As an aidm-ui operator, I want the engine manager to find the 2.7.0 manifest at the latest release, so that I can install a current engine without typing anything.
2. As an aidm-ui operator, I want the manifest signed by the key my interface already trusts, so that a tampered asset is refused.
3. As an aidm-ui operator, I want each variant pinned by digest with its download size, so that the install shows what it will pull and verifies what it pulled.
4. As an aidm-ui operator, I want the manifest to say the package accepts a socket, so that my Mac uses the socket from the first start.
5. As an aidm-ui operator, I want a manifest with a sequence above the built-ins, so that the install moves forward and never back.
6. As a maintainer, I want the tag run to verify its own signature against the committed public key, so that a wrong or rotated secret fails the run instead of publishing.
7. As a maintainer, I want a dry run to produce a manifest signed with a throwaway key, so that I can rehearse the whole path without the signing key leaving its environment.
8. As a maintainer, I want the dry run to check the manifest with aidm-ui's own verifier, so that a schema drift between the two repositories shows before a tag.
9. As a maintainer, I want the sequence derived from the version, so that no counter lives in the repository and nothing can drift.
10. As a maintainer, I want the minimum interface version in one place, so that the next release changes one line.
11. As a builder, I want a dry run to push all three images by digest to the CI package, so that the rehearsal manifest has three variants and the code that reads sizes runs on each.
12. As a builder, I want the manifest built by a script in this repository, so that the tag run checks out nothing else.
13. As a reviewer, I want the manifest job named for what it does and the image-tagging job renamed, so that "manifest" means one thing in the workflow.

### Reaching the API through a socket

14. As an aidm-ui operator on a Mac, I want the engine reached through a socket relayed by the container tool, so that a VPN or a local-network permission cannot take the engine away.
15. As an aidm-ui operator, I want the port to stay open inside the container, so that the check from inside keeps working.
16. As an engine manager, I want `socket` in the config file next to `port`, so that I write one file as I do today.
17. As an engine manager, I want a stale socket file removed at start, so that a restart after a crash works.
18. As an operator, I want the API to refuse to start when the socket path holds a file that is not a socket, so that a typo never deletes my file.
19. As an operator, I want the socket created with mode 0600, so that only the user the API runs as can open it.
20. As an operator, I want the socket removed at a clean stop, so that nothing is left behind.
21. As an operator on Windows, I want a clear error if I set the socket option, so that I know it is not supported there instead of guessing.
22. As a client, I want the same routes and the same token check on the socket as on the port, so that nothing else changes.
23. As a maintainer, I want the startup log to say which socket the API listens on, so that a diagnosis log has the fact.

### Creating a task from a folder

24. As an aidm-ui operator, I want the engine to read my imported folder where it is, so that a flight is not doubled on one disk.
25. As an aidm-ui operator, I want my photos untouched after a run, so that nothing is written into my folder.
26. As an aidm-ui operator, I want the interface to offer the folder path only on an engine that has the feature, so that a request never fails on an older API.
27. As an engine manager, I want to set the images root in the config file I write, so that the mounted folder is the only place the API reads from.
28. As an operator with an engine on this machine, I want to set the images root once at startup, so that my flights folder is accepted and nothing else.
29. As a client, I want `imagesPath` at the chunked init and at the single-request creation, so that both ways of creating a task take it.
30. As a client, I want the folder refused in the response when it cannot be read, lies outside the root or holds no accepted file, so that I know at creation and not from a failed task.
31. As a client, I want `imagesPath` with a zip address refused, so that two inputs never mix in one images folder.
32. As a client, I want to upload a ground control file next to a linked folder, so that ground control keeps working.
33. As an operator, I want every image and video the engine accepts taken from the folder's top level, including mask files, so that nothing is missed and subfolders are left alone.
34. As an operator, I want a hard link where the file system allows it, so that a run survives the folder being moved.
35. As an operator with a container engine, I want a symbolic link when a hard link cannot cross the mount, so that the feature works there too.
36. As an operator, I want the links removed with the task and never the photos, so that cleanup is safe.
37. As a client, I want a restart to reuse the images folder, links included, so that nothing has to be sent again.
38. As a client, I want `/info` to carry `imagesPath` only when the feature is on, so that an absent key means what it means today.
39. As a maintainer, I want the feature off without a root, so that no client can point a task at any folder the API user can read.

### Bundled tools

40. As an operator of a release archive, I want zip uploads and zip addresses to work without installing anything, so that the archive is enough.
41. As an operator of a release archive on Windows, I want the same, so that Windows is not the exception.
42. As an engine manager, I want the archive to need nothing on the operator's path, so that I can run it as a detached process on any machine.
43. As an operator, I want the licence of every bundled tool in the notices, so that redistribution is in order.
44. As a maintainer, I want the tools downloaded at build time from a pinned, checksummed source, so that no binary is committed and a changed download fails the build.
45. As a maintainer, I want the compiled executables tested with the bundled tool alone on every platform, so that the archive is proven, not assumed.
46. As a client, I want the error message for a corrupt zip to stay what it is, so that nothing I parse changes.
47. As an image user, I want the images untouched, so that the tools they install keep doing the work there.

### Removing the upstream fields

48. As a client, I want `/info` to describe the API by its own version, so that no field names a tracking relation that does not exist.
49. As a maintainer, I want the fields removed under a spec, so that the compatibility rule is kept, not broken.
50. As a reader of the changelog, I want the removal called out, so that I know before I upgrade.
51. As a harness maintainer, I want the golden files changed by that removal and nothing else, so that every other scenario stays exact.

### The release

52. As a maintainer, I want every file that states the version to say 2.7.0 and the version test to prove it, so that no file lags.
53. As a maintainer, I want the base image moved to engine 0.2.0, so that the GPU test runs the vineyard sets and the images carry the engine the manifest says.
54. As a reader of the changelog, I want one paragraph that tells the release as a whole and lines I can read, so that review-record numbers and process lines are gone.
55. As a maintainer, I want the dry run on the final branch as the rehearsal of the tag run, so that the tag run holds no surprise.
56. As a maintainer, I want the API tagged as soon as the engine tag exists and the tickets are merged, so that the UI can pin the published digests.
57. As a maintainer, I want to know which maintainer-side steps exist and in which order, so that nothing waits on a step nobody ran.

## Implementation decisions

### Signed release manifest (ADR 0001)

- One manifest per release, in the schema aidm-ui parses: `schemaVersion` 1, `sequence`, `packageVersion`, `engineVersion`, `minimumUiVersion`, `variants`.
- `sequence` is major x 1,000,000 + minor x 1,000 + patch. 2.7.0 carries 2007000.
- `minimumUiVersion` comes from a new `minimumUiVersion` key in the package file, set to 0.1.0.
- `engineVersion` comes from the base image tag the Dockerfile names, the same line the workflow's check job already parses.
- Three variants, `linux-amd64-cpu`, `linux-arm64-cpu`, `linux-amd64-gpu`, all container entries with `kind`, `image` without a tag, `digest`, `size`, `gpu`, and `taskApiSocket: true`. No native entries.
- Digests come from the per-platform digest artifacts the build jobs upload. Size is the sum of the compressed layer sizes plus the config size of the image manifest, read from the registry after the push.
- A Bun script in the scripts folder builds the manifest, signs it with a PKCS#8 PEM private key read from standard input, and verifies a signature against a public key file. It uses WebCrypto; no dependency is added. The JSON is written once with fixed formatting; the signature covers exactly those bytes, as a raw 64-byte file.
- Workflow: the current image-tagging job id becomes `tag-images`. A new job builds the manifest in every run, after the GPU test, and in a publish run after `tag-images`. A tag-only job declared with `environment: release` reads `MANIFEST_SIGNING_KEY` by name, signs, and verifies against the committed public key before upload; no other job names the environment. In a dry run a job with no environment generates a key, signs, verifies, uploads the manifest, its signature and the generated public key as one artifact, checks out aidm-ui at a commit pinned by full SHA with the already pinned checkout action, and runs that checkout's verifier with the generated key. The draft-release job uploads the manifest and the signature with the other assets.
- The public key is committed as one base64 line in `.github/manifest-public-key.txt`.
- Dry runs push all three images, untagged and by digest, to the CI package; the dry-run manifest names that package.
- A needed job skipped in a dry run skips its dependents unless the condition says otherwise; the builder minds that.

### Task API socket

- Config key `socket`, flag `--socket <path>`, no default. The API listens on the path with a second `node:http` server on the same application, so every route and the token check are the same on both. The port keeps listening.
- Before listening: nothing at the path is fine; a socket is removed; anything else fails the start with an error naming the path.
- The socket is created with mode 0600 and removed in the existing graceful shutdown on SIGTERM and SIGINT. The startup log names the socket.
- On Windows the option fails the start with an error saying it is not supported there.
- The check that Apple's relay can open the socket runs on the maintainer's Mac with the command in the design note, on a dry-run arm64 image that includes the socket code and the three-image push.

### A task from a folder (ADR 0002)

- Form field `imagesPath` at the chunked init and at the single-request creation. Capability key `imagesPath` with the value true in `/info` when the feature is on; no key when it is off.
- Flag `--images_root <folder>`, config key `imagesRoot`, no default. Without it the field is refused. With it, the request's path must resolve through real paths to a folder inside the root.
- Accepted files: the top-level regular files whose extension, matched without case, is in the engine 0.2.0 image list (`.jpg .jpeg .png .tif .tiff .bmp .raw .dng .nef .jxl`) or video list (`.mp4 .mov .lrv .ts`). Mask files are in by construction. The list is hard-coded in the API and recorded as the engine 0.2.0 list.
- Before the response of init and of the single-request creation: the root check, the readability check, the "at least one accepted file" check, and the links themselves, made into the task's staging folder where uploads land, so a link that cannot be made also fails the response. Commit moves them with the uploads, and the moved links satisfy the existing file count.
- Error cases, each an error in the response as the API reports errors today: feature not enabled; path outside the root; path cannot be read, with the reason; no supported image or video file; `imagesPath` with `zipurl`.
- Uploaded files alongside `imagesPath` stay allowed and land where they do today.
- Each link is a hard link first and, on any failure, a symbolic link whose target is the absolute real path of the source file. The source folder is never opened for writing. Removing a task removes its folder and with it the link entries. A restart reuses the images folder.
- Docs: the API specification and the Swagger file gain the field and the capability.

### Bundled tools (ADR 0003)

- Every release archive bundles one 7-Zip executable and no Info-ZIP `unzip`. Official 7-Zip 26.05 from its GitHub releases: `x64/7za.exe` from the Extra package on Windows, the static `7zzs` from the Linux x64 and arm64 archives. Pins in a checksum file next to the Bun sums.
- A new download script verifies the sums and unpacks; it uses the Linux `7zzs` it just fetched to open the Windows Extra package. The packaging script places the tool under `apps/7z/` in the archive. The notices generator takes each package's own licence text from the downloaded package.
- In a compiled executable the bundled tool is looked for next to the executable first and used for both extraction and `all.zip`. Path lookup (`unzip`, then `7z`) stays as the fallback, and as the whole rule in source mode and in the images.
- The harness treats "unzip exited with code 9" and "7z exited with code 2" as the same for the corrupt-zip step. The golden file and the API's error text do not change.
- The README's lines about installing the tools say: the archives bundle 7-Zip, the images install both, source mode needs them on the path.

### The upstream fields (ADR 0004, issue #69)

- `upstreamVersion` and `engineUpstreamVersion` leave `/info`, the startup log, the Swagger file, the API specification, the four golden files that record `/info`, the systeminformation unit test and the package file. The code that read the engine's file goes with them.
- The README describes the contract without a version: "compatible with the NodeODM task API" stays.
- One pull request, the first of the release, because later scenarios copy the `/info` steps from the updated golden files.

### The release ticket

- Every file the version test checks says 2.7.0. The CPU Dockerfile and the Apptainer definition move the base to engine 0.2.0, the GPU Dockerfile to its GPU tag.
- `## Unreleased` becomes `## 2.7.0`. The dependency lines and the process line become lines a user can read, with no review-record numbers. A paragraph at the top tells the release as a whole: engine 0.2.0, the first UI tag, the signed manifest, the socket, the folder path, the bundled tool, the two fields removed.
- Blocked by the engine tag `v0.2.0` and by every other 2.7.0 ticket. Its dry run is the rehearsal of the tag run.
- Tag order: the API tags when `v0.2.0` exists and every ticket is merged; the aidm-ui session pins the published digests and the manifest after that; the announcement waits for all three tags.

### The taggable minimum

1. #69 merged.
2. The manifest ticket merged: a dry run produced a three-variant manifest that aidm-ui's verifier accepted.
3. The socket ticket merged.
4. The folder ticket merged.
5. The tools ticket merged: the compiled executables passed the harness with the bundled tool alone on all three platforms.
6. Engine `v0.2.0` tagged.
7. The release ticket merged after its rehearsal dry run; then the tag is pushed and the tag run is green, with `manifest.json` and `manifest.json.sig` on the draft release.

## Testing decisions

A good test checks what a client or an operator sees: a response, a file in the archive, a link in the images folder, an asset on the release. It does not check how the code got there. The compatibility harness in test mode is the highest existing seam and is preferred wherever a scenario can express the behaviour; unit tests cover what the harness cannot reach (a script, a refusal at startup, a file system property). The dry run is the only seam for the workflow itself.

### Seams

- Compatibility harness, test mode: one new scenario per feature that changes a response. `socket` (every request through the socket, skipped on Windows), `images-path` (`/info` with the capability and a task from a folder under the tests folder). Existing golden files change only in #69.
- Unit tests under the unit folder, in the pattern of the storage, move and error-path tests: child-process starts of the API where a flag is under test, temporary folders, no network beyond loopback.
- The dry run of the release workflow, started by the maintainer on the pull request head when the pull request is open and linked in the description, so the reviewer judges its results as `REVIEW.md` requires.
- The maintainer's Mac, for the one check no runner can do: Apple's relay opening the socket.

Five dry runs at minimum, one per `full` pull request, asked for when the pull request is open. A second only if the head moves after it. At most three in parallel. Order: #69, then #25 and #8 in sequence (both edit the release workflow), #47 and #34 whenever ready, the release ticket last.

Prior art: `tests/unit/storage.test.js` and `tests/unit/http-client.test.js` start a server on loopback; `tests/unit/task-uuid.test.js` and `tests/unit/postprocess.test.js` use child processes; `tests/unit/check-pushed-image.test.js` runs a shell script from the scripts folder against cases; `tests/compat/run.js` holds the scenarios and the normalisation.

## Out of scope

- #24 macOS executable: needs a macOS engine build (aidm #15). The 7-Zip macOS archive exists for that day.
- #15 API quirks (every error as HTTP 200, other uploaded zips deleted): contract changes for the maintainer to decide, not this release.
- #12 `contrib/` and #13 dev tooling.
- #67 the test-mode GLB placeholder: fixed on its own.
- The Modal GPU test on every master push: a later workflow-only pull request when aidm-bench needs API images for master.
- The lint job and `ci-paths.yml`: after the tag.
- Any dispatch, scheduling or multi-machine work.
- Benchmarks: nothing here changes an engine run. A ticket that turns out to change task throughput files a request in aidm-bench at review clear and measures nothing.

## Further notes

- Values the aidm-ui session matches: `sequence` 2007000; `minimumUiVersion` 0.1.0; `taskApiSocket: true` on each container variant; config key `socket`; field and capability `imagesPath`, with `imagesRoot` set by the engine manager; the public key value in `.github/manifest-public-key.txt`; assets `manifest.json` and `manifest.json.sig`.
- The maintainer: checks the `modal-gpu` environment's branch policy covers every builder branch prefix before the first dry run; starts each dry run on the pull request head when asked; runs the socket check on his Mac after #34 and #25 are merged; publishes the draft release when the tag run is green, after `v0.2.0` exists; re-pins aidronemap.dev to `v2.7.0`.
- Nothing here needs a new secret, environment or repository setting.
- The scratch-machine findings behind the tools decisions (a RAR-free source build, the extraction comparison, the harness with 7-Zip alone) are diagnostics recorded in the design note, never claims.
